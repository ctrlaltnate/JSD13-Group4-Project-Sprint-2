## 1. แนวคิดหลักของระบบ
ระบบออกแบบโดยยึดหลักต่อไปนี้

1. ข้อมูลสารอาหารเก็บที่วัตถุดิบ ไม่ได้กรอกซ้ำในแต่ละเมนู
2. วัตถุดิบรวมทั้งวัตถุดิบสด เครื่องปรุง ซอส ผงปรุง และส่วนผสมสำเร็จรูป
3. ค่าสารอาหารอ้างอิงต่อวัตถุดิบ 1
00 กรัม และวัตถุดิบไม่จำเป็นต้องมีสารอาหารครบทุกประเภท
4. คุณค่าทางโภชนาการของเมนูคำนวณจากวัตถุดิบและปริมาณที่ใช้ในสูตร
5. ขั้นตอนการทำอาหารถูกแยกเป็นขั้นตอนหลักและ Process ย่อย
6. ตารางกลางใช้แก้ความสัมพันธ์แบบ Many-to-Many เช่น เมนูกับวัตถุดิบ และวัตถุดิบกับสารอาหาร

### 3.8 `NUTRIENT`

คลังนิยามสารอาหาร ไม่ผูกกับวัตถุดิบชนิดใดโดยตรง

| Field | หน้าที่ |
|---|---|
| `nutrient_id` (PK) | รหัสสารอาหาร |
| `nutrient_name` | ชื่อ เช่น Protein, Vitamin C, Iron |
| `nutrient_category` | Macronutrient, Vitamin, Mineral หรือ Other |
| `default_unit` | หน่วยมาตรฐาน เช่น `g`, `mg`, `µg` |

หน่วยของสารอาหารไม่ควรกำหนดเป็นกรัมทั้งหมด เพราะวิตามินและแร่ธาตุบางชนิดเหมาะกับ `mg` หรือ `µg`

### 3.9 `INGREDIENT_NUTRIENT`

ตารางกลางสำหรับค่าของสารอาหารแต่ละชนิดในวัตถุดิบ

| Field | หน้าที่ |
|---|---|
| `ingredient_nutrient_id` (PK) | รหัสรายการ |
| `ingredient_id` (FK) | วัตถุดิบ |
| `nutrient_id` (FK) | ชนิดสารอาหาร |
| `amount` | ปริมาณสารอาหาร |
| `basis_weight_g` | น้ำหนักวัตถุดิบที่ใช้เป็นฐาน โดยทั่วไปคือ 100 |

ตัวอย่าง: ขิง 100 กรัมมี Vitamin C 5 mg

```text
ingredient_id  = ขิง
nutrient_id    = Vitamin C
amount         = 5
basis_weight_g = 100
หน่วย          = mg จาก NUTRIENT.default_unit
```

วัตถุดิบหนึ่งรายการไม่จำเป็นต้องมีสารอาหารครบทุกชนิด หากไม่มีข้อมูลไม่ต้องสร้างแถว และไม่ควรบันทึกเป็นศูนย์ เว้นแต่ยืนยันได้ว่าค่าเป็นศูนย์จริง

ควรกำหนด `UNIQUE(ingredient_id, nutrient_id, basis_weight_g)` เพื่อป้องกันข้อมูลซ้ำ

## 5. การคำนวณสารอาหารของเมนู

สมมติวัตถุดิบมีสารอาหาร `amount` ต่อ `basis_weight_g` และสูตรใช้วัตถุดิบ `used_weight_g`

```text
สารอาหารจากวัตถุดิบ
= amount × (used_weight_g / basis_weight_g)
```

ตัวอย่าง ขิงมี Vitamin C 5 mg ต่อ 100 g และสูตรใช้ขิง 20 g:

```text
5 × (20 / 100) = 1 mg
```

สารอาหารรวมของเมนูคือผลรวมจากวัตถุดิบทุกตัว:

```text
สารอาหารรวมของเมนู
= SUM(สารอาหารของวัตถุดิบแต่ละรายการในสูตร)
```

หากสูตรมาตรฐานทำได้หลาย Serving ให้หารผลรวมด้วยจำนวน Serving ก่อนแสดงค่าต่อหนึ่ง Serving

ค่าที่ไม่มีข้อมูลต้องแสดงเป็น “ไม่มีข้อมูล” หรือ `null` ไม่ควรตีความเป็นศูนย์ เพราะอาจทำให้คำแนะนำสุขภาพผิดพลาด

## 6. ตัวอย่างการนำไปใช้

### 6.1 แสดงรายละเอียดเมนู

1. อ่านข้อมูลจาก `DISH`
2. อ่านรายการวัตถุดิบจาก `RECIPE_INGREDIENT`
3. อ่านขั้นตอนจาก `COOKING_STEP` เรียงตาม `step_number`
4. อ่าน Process ย่อยจาก `COOKING_SUB_STEP` เรียงตาม `sub_step_number`
5. คำนวณสารอาหารผ่าน `INGREDIENT_NUTRIENT`

### 6.2 ตรวจสอบเมนูกับการแพ้อาหาร

1. ดึง `ingredient_id` ที่ผู้ใช้แพ้จาก `USER_ALLERGY`
2. ดึง `ingredient_id` ของเมนูจาก `RECIPE_INGREDIENT`
3. ตรวจว่ามีรายการตรงกันหรือไม่
4. หากตรงกัน ให้เตือนหรือซ่อนเมนูตามนโยบายระบบ

ควรตรวจส่วนประกอบของเครื่องปรุงผสมด้วย หากซอสหนึ่งชนิดมีส่วนประกอบย่อย ระบบระยะถัดไปอาจเพิ่ม `INGREDIENT_COMPONENT` เพื่อรองรับวัตถุดิบซ้อนกัน

### 6.3 ค้นหาเมนูตามสารอาหาร

ระบบสามารถรวมค่าจากสูตรเพื่อค้นหา เช่น:

- เมนูโปรตีนสูง
- เมนูโซเดียมต่ำ
- เมนูที่มี Vitamin C
- เมนูที่ไม่มีวัตถุดิบก่อภูมิแพ้ของผู้ใช้

### 6.4 การสั่งซื้อ

1. สร้าง `ORDER`
2. สร้าง `ORDER_ITEM` สำหรับแต่ละเมนู
3. คำนวณ `total_amount` จาก `quantity × unit_price`
4. อัปเดต `order_status` ตามกระบวนการจัดเตรียมและจัดส่ง
5. เมื่อคำสั่งซื้อสำเร็จ สร้าง `STAMP_TRANSACTION` ภายใน Database Transaction เดียวกัน

### 6.5 Subscription และเมนูรายสัปดาห์

1. ตรวจ `SUBSCRIPTION.status = Active`
2. อ่านจำนวน Kit จาก `plan_type`
3. ให้ผู้ใช้เลือกเมนูและสร้าง `WEEKLY_MEAL_SELECTION`
4. ตรวจจำนวนรายการต่อสัปดาห์
5. ป้องกันการแก้รายการหลังพ้น Cut-off Time ตามกฎธุรกิจ

## 7. ข้อกำหนดและ Validation ที่แนะนำ

- จำนวน ราคา น้ำหนัก และค่าสารอาหารต้องไม่ติดลบ
- `basis_weight_g` และ `reference_weight_g` ต้องมากกว่า 0
- `step_number` และ `sub_step_number` ต้องมากกว่า 0
- `end_date` ต้องไม่ก่อน `start_date`
- `quantity` ใน `ORDER_ITEM` ต้องมากกว่า 0
- ใช้ Decimal เช่น `DECIMAL(12,4)` สำหรับน้ำหนักและสารอาหาร ไม่ควรใช้ Float หากต้องการความแม่นยำ
- ทุก Foreign Key ควรสร้าง Index
- ใช้ `ON DELETE RESTRICT` กับข้อมูลอ้างอิงสำคัญ เช่น วัตถุดิบที่ถูกใช้ในสูตร
- ใช้ Soft Delete หรือ `is_active` กับเมนูและวัตถุดิบที่เคยมีประวัติการสั่งซื้อ
- บันทึก `created_at` และ `updated_at` ในตารางหลักเมื่อนำไปสร้างฐานข้อมูลจริง

## 8. ตารางที่อาจเพิ่มในอนาคต

| ตาราง | เหตุผล |
|---|---|
| `UNIT_CONVERSION` | แปลงช้อนโต๊ะ ช้อนชา ถ้วย หรือชิ้นให้เป็นกรัม |
| `INGREDIENT_COMPONENT` | แตกส่วนประกอบของซอสหรือเครื่องปรุงผสม |
| `SUBSCRIPTION_PLAN` | แยกรายละเอียดและราคาของแพ็กเกจออกจากประวัติการสมัคร |
| `ADDRESS` | รองรับหลายที่อยู่ต่อผู้ใช้ |
| `PAYMENT_TRANSACTION` | เก็บช่องทาง สถานะ และ Reference การชำระเงิน |
| `DELIVERY` | แยกข้อมูลขนส่งและ Tracking |
| `NUTRIENT_SOURCE` | ระบุแหล่งอ้างอิงหรือผลตรวจของค่าสารอาหาร |
| `RECIPE_VERSION` | เก็บประวัติการเปลี่ยนสูตรและค่าสารอาหารย้อนหลัง |

## 9. สรุป

โครงสร้างนี้ทำให้ข้อมูลสารอาหารมีความยืดหยุ่น เพราะเพิ่มชนิดสารอาหารใหม่ได้โดยเพิ่มแถวใน `NUTRIENT` ไม่ต้องแก้คอลัมน์ของวัตถุดิบ และแต่ละวัตถุดิบสามารถมีสารอาหารเท่าที่มีข้อมูลจริง เมนูใช้สูตรเชื่อมไปยังวัตถุดิบเพื่อคำนวณสารอาหารแบบ Dynamic ขณะเดียวกันยังรองรับการแพ้อาหาร วิธีทำแบบหลายระดับ Subscription คำสั่งซื้อ และการเลือกเมนูรายสัปดาห์ในฐานข้อมูลเดียวกัน
